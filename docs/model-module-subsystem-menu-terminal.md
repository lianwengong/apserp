# 功能模块 / 子系统 / 终端 / 菜单 —— 关系说明

> 目的：把四个容易混为一谈的概念分开，说明它们在**数据库里怎么存**、**运行时怎么串**、
> **现在哪里是重复的或空的**，最后给出三种收敛方案（需负责人拍板）。
>
> 数据取自开发库 `APSErpV3`（V40 之后），数字都是实际 `SELECT COUNT(*)` 的结果。

---

## 1. 一句话定义

| 概念 | 是什么 | 不是什么 | 代码位置 |
|---|---|---|---|
| **子系统** | 交付与验收单位：有独立负责人、验收清单、上线开关。按「平台 / 终端 / 业务 / 集成 / 工程」五层划分（方案里 57 个） | 不是树节点，不参与运行时鉴权 | **当前系统没有这个实体**（仅存在于《开发方案》文档） |
| **功能模块** | 权限与配置的组织单位：模块树 + 功能点 + 动作链，产出 `MOD:`/`FUN:` 权限点 | 不是导航项，用户不会"点一个模块" | `plat.Module` / `plat.ModuleFunction` / `plat.FunctionAction` |
| **菜单** | 给人点的导航入口：一棵独立树，挂在侧边栏 | 不等于模块（可以一条菜单不绑模块） | `plat.Menu` / `plat.MenuTerminal` |
| **终端** | 渠道：PC / PDA / POS / 移动 / 小程序 / 其他（1..6） | 不是设备实例，是"哪类界面" | `plat.MenuTerminal.TerminalType` |

关键区分：

- **模块决定「有没有权限」，菜单决定「在哪个设备、哪个位置点进去」**。
- 同一个人、同一个权限，在 PC 上看到的菜单可能比 PDA 多 —— 差异只由 `MenuTerminal` 表达。
- 子系统是「人和交付」的单位，不是运行时概念；不要把它硬塞进鉴权链。

---

## 2. 关系总览

```
【概念层】
  子系统(57，交付/验收单位)
     │ 1 : n    一个子系统由哪些模块实现
     ▼
【配置层】
  功能模块(plat.Module，树：业务域 → 模块 → 功能节点)
     │ 1 : n
     ├──► 功能点(ModuleFunction) ──1:n──► 动作链(FunctionAction)
     │         └── 产出权限点  FUN:功能点编码
     └── 产出权限点  MOD:模块编码（每一级模块一条）
     │
     │ n : 1（可选绑定，弱引用）
     ▼
  菜单(plat.Menu，独立树) ──n:1(可选)──► 页面(plat.Page)
     │
     │ n : n
     ▼
  终端(plat.MenuTerminal)  ← 运行时唯一真正生效的终端过滤点

【运行时层】
  登录 → 租户(RLS) → 终端号(1..6) → 菜单树过滤(MenuService) → 权限点过滤(父节点有可见子则保留) → 渲染
```

三条硬约束（代码里已经生效）：

1. **菜单不绑模块也能显示**，但这样就没法用 `MOD:`/`FUN:` 授权，只能靠「平台管理员」整体放行；
2. **权限点过滤以叶子为准**：叶子节点没有 `MOD:`/`FUN:` 授权就整枝消失（`MenuService.filterTree`）；
3. **终端过滤只在菜单层**：模块层没有参与判定。

## 3. 当前实际形态（实测数字）

### 3.1 功能模块：三层，636 条

| 层级 | 数量 | 含义 | 例子 |
|---|---|---|---|
| Level 1 | 10 | 业务域（`ModuleType=1` 目录） | `01 主数据`、`02 采购与供应商` … `10 计划与决策` |
| Level 2 | 62 | 模块（`ModuleType=2`） | `0101 组织与门店`、`0102 商品与主数据` … |
| Level 3 | 564 | 功能节点（`ModuleType=2`，一个具体功能） | `010101`、`070705 PDA拣货复核` … |

- **功能点 1436 条全部挂在 Level 3**（Level 1/2 没有功能点）；
- 动作链 `FunctionAction` 0 条（表在、功能在，但还没配置任何动作链）；
- 权限点：`MOD:` 638、`FUN:` 1436、`DATA:` 3、`DESIGN:` 7。

### 3.2 菜单：677 条，其中 636 条与模块 1:1 镜像

| 分区 | 条数 | 绑模块 | 绑页面 | 说明 |
|---|---|---|---|---|
| 业务菜单（01..10 子树） | 636 | 全部 | 0 | **与模块树一一对应**：10 + 62 + 564 = 636 |
| 平台管理（`90` 子树） | 41 | 0 | 1 | V38 新增，纯菜单、无模块，只能靠平台管理员放行 |

> 也就是说：**改一个模块名，必须同步改一条菜单名**，这是当前最大的重复维护点。
> 另外 676 条菜单没有绑定页面（`PageId IS NULL`），其中 589 条直接落到 `/m/{code}` 占位页 —— 占位页只证明"入口存在"，不代表功能已实现。

### 3.3 终端：菜单层有数据，模块层是空壳

| 表 | 行数 | 状态 |
|---|---|---|
| `plat.MenuTerminal` | 1058 | **在用**（本租户未删菜单）：PC 636、POS 84、移动 130、小程序 114、其他 65、PDA 29 |
| `plat.ModuleTerminal` | 0 | **未使用**（表由 V2 创建，没有任何代码读写） |

同一件事存在两个"声明位置"，实际只有菜单层生效 —— 这是最容易误解的地方。

## 4. 运行时判定链（用户到底能点开什么）

```
1. 租户隔离     SESSION_CONTEXT + RLS            → 只能看到本租户配置
2. 终端过滤     MenuTerminal.TerminalType        → 只保留该终端的菜单
3. 状态过滤     Menu.IsDeleted=0 / IsEnabled=1 / IsVisible=1
4. 权限过滤     MOD:xxx / FUN:xxx / MOD:xxx.*    → 叶子无权限则整枝移除；父节点有可见子则保留
5. 路由解析     Route 优先；没 Route 但绑了 Page 用 /m/{code}；都没有 → 点击无反应（需补）
```

菜单点击后可能落到三类页面：

| 目标 | 例子 | 说明 |
|---|---|---|
| 元数据列表页 | `/object/md.brand` | 引擎渲染，真正有功能 |
| 设计器页 | `/design?tab=rule` | 配置界面 |
| 占位页 | `/m/900202` | 菜单存在、页面未建 |

## 5. 现在不清晰 / 有风险的 5 处

| # | 问题 | 后果 | 影响面 |
|---|---|---|---|
| 1 | **模块与菜单 1:1 双写**（636 vs 636） | 改名/挪位要改两处，必然漂移 | 全部业务菜单 |
| 2 | **终端两处声明**：`ModuleTerminal` 空表、`MenuTerminal` 在用 | 新人按模块配终端，配完不生效 | 所有终端差异 |
| 3 | **41 条平台管理菜单不挂模块** | 无法用 `MOD:`/`FUN:` 授权，只能"平台管理员全放" | 平台控制台 |
| 4 | **子系统缺位**（57 个只存在于文档） | 交付/验收无法在系统里表达"谁负责哪个子系统" | 项目管理、上线开关 |
| 5 | **两套编码**：模块 `0101` / 菜单 `01.01.01` / 业务域 `01` | 同一业务对象三种编码，关联靠人眼 | 排障、迁移 |

## 6. 三种收敛方案

### 方案 A：维持现状，只补约束（最小改动）

- 菜单必须绑模块（新增校验；平台管理菜单除外）
- 删除 `plat.ModuleTerminal`，或明确"模块不声明终端"
- 菜单编码强制 = 模块编码派生

**代价**：双写问题仍在（只是被约束住）。**适合**：短期交付优先。

### 方案 B（推荐）：三层定死，菜单是模块的"终端投影"

```
子系统 = Level 1 业务域（10 个）         ← 复用现有模块树根，不新增实体
模块   = Level 2/3（62 + 564）           ← 权限、配置、功能点的唯一归属
菜单   = 模块在某终端下的入口             ← 由模块自动派生，Code = 模块 Code + 终端后缀
```

- 菜单变成 **模块的投影**：新增模块时按「勾选的终端」自动生成 1..n 条菜单；
- 菜单上只保留"入口差异"字段（图标覆盖、排序、角标、打开方式）；
- 平台管理子树建一个"伪模块"（`Code=90`），让 41 条菜单也能被 `MOD:` 管控；
- `ModuleTerminal` 启用为"模块默认终端"，菜单终端默认继承它（可单条覆盖）。

**代价**：要写一次数据迁移（把 636 条菜单的 Code 改成派生规则）。**适合**：要长期维护 500+ 功能节点。

### 方案 C：新增 `plat.SubSystem` 实体（跨层）

- 新表：`Code / Name / Owner / Layer(平台|终端|业务|集成|工程) / Enabled / 上线开关`
- `plat.Module` 加 `SubSystemId`
- 一个子系统可跨多个业务域（对应方案里"平台层 20 个、集成 15 个"这类跨域子系统）

**代价**：表 + 外键 + UI + 迁移；但能完整承载 57 个子系统的交付语义。**适合**：要把"验收/上线开关"做成系统能力。

### 对比

| 维度 | A | B | C |
|---|---|---|---|
| 解决双写 | 部分 | ✅ | ✅ |
| 终端语义清晰 | 部分 | ✅ | ✅ |
| 承载 57 子系统 | ❌ | 部分（只有业务域 10） | ✅ |
| 改动量 | 小 | 中（一次迁移） | 大 |
| 风险 | 漂移 | 迁移要停机窗口 | 架构决策 |

## 7. 如果选 B，落地清单（预估 1 天）

1. **迁移 V41**
   - 平台管理建伪模块 `90 平台管理`（`ModuleType=1`）+ Level2 模块承接 41 条菜单
   - 菜单 `Code` 统一改为 `模块Code` 派生；重复 Code 合并
   - `ModuleTerminal` 按菜单终端回填（作为默认值）
2. **服务端**
   - `MenuAdminService.save`：新增菜单时若绑了模块，Code 必须等于模块 Code（或自动生成）
   - `MenuService.tree`：终端过滤改为「菜单终端 优先，缺省取模块终端」
   - 新增 `POST /api/admin/modules/{id}/menus/sync`：按勾选终端生成/修复该模块的菜单
3. **前端**
   - 模块管理窗口增加「菜单投影」区域（显示该模块在各终端的菜单、一键同步）
   - 菜单窗口改为"只改入口差异字段"，Code/模块不可随手改
4. **测试**
   - 模块改名 → 菜单同步断言
   - 终端继承链路：模块声明 PDA → 菜单默认 PDA → 单条覆盖为 PC
   - 平台管理伪模块的 `MOD:` 授权生效断言

## 8. 需要负责人拍板的三件事（架构决策，AI 不自行决定）

1. **选 A / B / C**（本文档推荐 B）；
2. `plat.ModuleTerminal` 是**启用**（模块默认终端）还是**删除**（终端只在菜单层）；
3. 平台管理那 41 条菜单，是**建伪模块纳入权限体系**，还是**继续只给平台管理员**。
